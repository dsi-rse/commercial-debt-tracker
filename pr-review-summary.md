# PR Review: Lifecycle and schema cleanup: stop deriving a status, bump the schema, and refuse cross-borrower lineage links

## Verdict: APPROVE WITH COMMENTS

## Overview

This pull request does two separable things. About 85% of it deletes a feature: the matcher used to work out a five-value lifecycle status for every debt instrument, and this removes it along with the four columns it published. The last commit adds one new behaviour: the lineage guesser now refuses to link two agreements when the filings name different borrowers.

**Every number in the description reproduces exactly, and the central claim holds.** I re-ran the matcher against the 542-instrument corpus already on disk, in throwaway copies of the code at the base branch and at each commit. Removing the cascade takes away exactly the four `status_*` columns, adds nothing, and leaves all 38 remaining columns byte-for-byte identical across all 542 rows, with the same 3 inferred links and the same 535 lineage heads. The argument *for* removing it reproduces too: moving the reference date backwards changed 49, 184, 198 and 218 statuses out of 542, and changed **nothing else at all**. Those are the four figures in the description's table. A reviewer repeated this independently with a full forced rematch and also found the mention-to-cluster edge table unchanged. The test suite passes (499 tests, 1 expected failure), the linter and formatter are clean at the repo's pinned version, and all five CI checks are green.

The new borrower guard works, and it is better than it looks from the diff. On the real corpus it fires four times. Two of those are the EQT/EQM case the commit describes: it detaches an acquired subsidiary's dead facility from the parent's chain, and because it sits inside `offer()` rather than filtering afterwards, it also *rescues* a link — EQT's Fourth Amended and Restated Credit Agreement had two candidate parents and was being discarded as ambiguous; with the wrong one gone it resolves. A filter applied after the fact would only have done the first half. The guard also respects the boundary the architecture document sets: it refuses matches, it never asserts a fact, and it reads only data the extractor already recorded and cited.

**The one thing I would handle before this reaches published data: the guard cannot undo a bad link that an earlier run already wrote.** `infer_amendment_parents` only looks at rows whose amendment pointer is empty, and the ordinary match path copies the existing pointer forward from disk. So the EQT/EQM error this commit exists to fix survives on any artifact root that has already been matched, and the next routine `cdt match` republishes it. I reproduced this directly: with the guard active, re-running the pass over a state where the bad link was already published leaves it exactly where it was. Measured across the corpus, carrying forward differs from a clean rebuild on 14 of 542 amendment pointers — every one of them a pointer the carry-forward keeps and the rebuild does not. The stickiness itself is pre-existing design, not something this PR introduced, and a forced rebuild is verified safe here (the instrument ID set is identical before and after). But it means commit 5's fix does not reach the data it was written for, and the description does not mention needing `--force`. I have marked this Important rather than High because the code is correct and the remedy is one command — but it would become High if the branch merges and the artifact root behind the beta gets refreshed with a plain match.

Beyond that, twelve findings are worth acting on, and five of them sit in the 69 lines of new guard code. Two are precision problems I verified by running the real functions against the real corpus. First, **a placeholder name counts as disagreement**: when a filing only ever calls the borrower by its own defined term, the extractor records the borrower as literally `"Issuer"`, so the guard reads `"HSBC Holdings plc"` against `"Issuer"` as two different companies and refuses the link. Seventeen rows carry such placeholder names, ten of them with nothing else recorded. That contradicts the guard's own docstring, which says it fires only on positive evidence. Second, **the prefix rule lets a subsidiary pass as its parent**: `"EQT Corporation"` and `"EQT Midstream Partners, LP"` are treated as one borrower, as are `"Ford Motor Company"` and `"Ford Motor Credit Company LLC"`. The EQT case the commit is built around works only because `eqt` and `eqm` differ in their first letter — and EQM Midstream Partners was itself renamed *from* EQT Midstream Partners, the name its 2018 agreement was signed under. Both problems are currently latent: switching to exact matching changes no link on this corpus, which two of us confirmed separately.

The test picture is uneven in a way that explains why those two problems are there. Of eleven mutations applied to the new guard, five were caught. The tests that exist are very good — one reconstructs the real EQT filing and kills three separate mutants including deletion of the whole call site, and another pins the subtle "a missing borrower is not a disagreement" rule whose removal would have switched off every inferred link in the corpus. But the one test named for legal-form suffixes passes for two different reasons at once, so a contributor can delete the entire nineteen-line suffix list, *or* replace the prefix rule with plain equality, and the suite stays green either way. The `prior_fact` rule, which the guard also gates, has no test of the new behaviour at all. The surviving half of the old rollup, by contrast, is genuinely well pinned: all seven mutations applied there were caught.

Two things were clearly overlooked in an otherwise disciplined deletion. A test marked `xfail(strict=True)` now fails with `ImportError`, because it imports the very function this PR deletes — and since `xfail` only checks *that* a test failed, not why, it stays green and keeps reporting the repo as carrying one known unfixed bug that can no longer exist. And `PreparedMention.status_date` is now written and read by nothing, which is precisely the rule the second commit's message declares it is enforcing. Alongside those, four one-line documentation statements were falsified by this PR's own edits, including the docstring on the public entry point behind `cdt match --infer-lineage`, which still promises it keeps `status` consistent.

**A suggestion on sequencing.** Commits 1 through 4 are verified clean: byte-identical output, no stale references, no surviving reader, and safe in both directions on existing parquet data. Commit 5 carries the stale-pointer gap and five of the twelve Important findings. If it suits you, merging the removal now and taking the borrower guard as its own change would let the tightening, the extra tests and the rebuild step land without holding up work that is already proven correct.

How this review was done, since it affects how much to trust each claim: four reviewers each took one concern (correctness, test coverage, repo coherence, and data safety), and I re-checked every finding against the full file before it reached this summary, dropping or downgrading what did not survive. The three findings about the guard's precision were found independently by me and by the correctness reviewer from different starting points, and I reproduced the stale-pointer finding myself after the data-safety reviewer raised it. Every number quoted here came from a command that actually ran, against artifacts already on disk, with no new model calls. Two process notes: I archived the previous review of #177 to `pr-review-findings-177.md` and `pr-review-summary-177.md` before writing these files, and all experiments ran in throwaway git worktrees — afterwards I confirmed no tracked file in this checkout was modified and the suite still passes.

## Things worth saying out loud

- **The evidence in this PR is unusually good.** Every headline figure reproduced on the first attempt. The `#196` paragraph in `docs/schema.md` states the removal, the reason, the measurement, the negative evidence and where the capability went, with a working issue link. Writing down why something is *absent* is rare, and it is what stops the next person re-adding it.
- **The deletion is disciplined.** Twenty removed symbols, zero stale references across `src/`, `docs/`, `scripts/`, the LLM prompt templates, CI config and infrastructure — all swept. The mention-level `status` column, which must survive, does; the instrument-level one, which must not, does not. That distinction was maintained correctly everywhere.
- **The guard is in the right place.** Putting it in `offer()` rather than in a post-filter is why it rescues a link as well as removing one, and it obeys the stage boundary the architecture document sets: it refuses, it never asserts.
- **The migration is safer than it had to be.** A mixed old/new partition set reads fine in either fragment order, one ordinary match converts a whole root, rollback works and costs one run, and the output is hash-seed independent and idempotent after one cycle. As a bonus, the rewrite actually *heals* an existing root whose mixed column types currently make `pyarrow.dataset` raise.
- **`maturity_date`'s documentation fix was not required by this issue.** The old bullet described the behaviour #162 fixed rather than the fix, so a reader reasoning about maturity provenance had it backwards. Correcting it here was a real improvement, and flagging the unfinished generalization was honest.
- **The old rollup's surviving logic is genuinely well tested** — all seven mutations applied to it were caught, and the schema tripwires (pinned version, exact column list) mean neither the four removed columns nor a fifth can move silently.

## One note on the net effect of commit 5

The description says the borrower guard recovers a link and the real predecessor "regains its `superseded_by`". Both are true. What it does not say is that resolving the Fourth Amended and Restated Credit Agreement gives the 2022 agreement a second child — the other being a duplicate cluster of the same 2024 agreement, caused by the naming bug listed under "Not fixed here" — so the ambiguity rule strips *its* `superseded_by`. Measured on the corpus: one row gains a pointer, one loses it, the total stays at 6, and lineage heads stay at 535. The pointer that remains is the correct one, so this is still a quality improvement — but anyone who measures the counts after merging will see no movement, and it is worth saying so in the description.
