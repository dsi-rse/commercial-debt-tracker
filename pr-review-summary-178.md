# PR Review: Pre-beta schema: kind-typed amounts and dates, parties, status events, provenance, lifecycle rollup

## Verdict: REQUEST CHANGES

## Overview

This PR rewrites what a debt instrument is in this pipeline: amounts and dates become kind-typed fact lists, parties collapse into one list with roles, lifecycle status is derived by a new rollup, and every published value carries a pointer to the mention it came from. It is 2,982 added source lines across 12 files from 29 commits, closing about twenty issues. The work is careful and unusually well documented — nearly every new constant and branch names the real filing that motivated it, which is the only reason a change this size was reviewable at all.

I checked the claims rather than taking them on trust, and they hold up. Recomputing the five judge-free metrics from the local run output reproduced seven of ten cells exactly; the three that differ are definitional, and both differences move the branch's own number in the unfavourable direction. The headline #154 claim is the strongest result: I re-sliced 11,656 published evidence spans out of the original item text and found zero mismatches, against three in the `dev` arm. The known gaps are reported honestly too — the PR body says 537 of 542 instruments publish as lineage heads and 54 revert to `announced`, and both numbers match the artifacts exactly. The test suite passes (394) and ruff is clean.

Two things drive the verdict. First, a genuine correctness problem: because every mention ID changes and `MATCHER_SCHEMA_VERSION` is written but never read, a match run without `--force` against an older artifact root silently publishes rows pointing at mentions that no longer exist, with lifecycle columns reset. I reproduced a published `terminated` instrument coming back as `active` with zero observation counts. That is not the same as issue #107 ("the root needs a rebuild"), which is a known gap — it is that a *partial* rebuild produces wrong rows and says nothing.

Second, and more decisive: the PR's central deliverable has no test protecting it. A mutation pass of 118 source edits killed only 60%, and I personally re-ran the three worst. Deleting `status`, `status_date` and `status_source_mention_id` from the published column list: 394 passed. Stripping `char_start`/`char_end` out of every evidence span — the whole point of #154: 394 passed. Making the new `validate_parties_property` return an empty list: 394 passed. No test anywhere references the column lists or the schema version. Individually these are Important, not High, since the HIPPO scale puts missing tests at Important — but they cluster on one risk, which is what moves the verdict.

The rest is a long tail of smaller findings, most of them one-line fixes: validator gaps that let malformed shapes through silently instead of retrying, three rules the validator enforces that the prompt never states (so retries get spent on shapes the model was never warned about), one worked example in the prompt that fails validation when followed, and four factual errors in `docs/schema.md` — which matters because that file is the contract the pending publisher work will be written against. None of these corrupt extraction; they mostly cost retries or drop a field quietly.

Worth saying plainly: none of this contradicts the eval's "merge, do not ship to beta yet" recommendation, and nothing I found undermines the A/B result. The findings are about the seams — incremental runs, legacy replay, and the absence of tests on the new schema — not about whether the new extraction is better. It clearly is.

## Inline notes

### src/cdt/matcher/core.py

- **L40, L597-649, L1387-1394** `HIGH` `[correctness]` **A match run without `--force` on an older artifact root silently publishes broken rows** — Every mention ID changes in this PR, and `MATCHER_SCHEMA_VERSION` went 3→4 but nothing reads it back: both uses only write it into a manifest. So an incremental match against a stale root produces three silent failures at once. Edge rows and `seed_debt_instrument_mention_id` point at mentions that are not in the dataset. Lifecycle columns are recomputed from an empty member list, so a published `terminated` instrument comes back as `active` — I reproduced exactly that, along with `mention_count` dropping from 1 to 0. Please gate on the recorded `schema_version` and either refuse or force when it is lower, and carry the existing row's status forward when the filtered member list is empty.

- **L1392, L1398, L1404** `IMPORTANT` `[correctness]` **The #153 CIK conversion missed the site that writes the published column** — Three read sites moved to `coerce_optional_cik`; the write site still uses `coerce_optional_text`. One run shows all three consequences: a legacy row publishes `707605` beside a new row's `0000707605`; its `company_name` blanks because the L1429 fallback looks up an unpadded key in a dict keyed by the padded form (that fallback exists specifically to stop a blank page, #47); and its legacy `lenders_json` is dropped, while `amount`→`principal_amount` and `end_date`→`maturity_date` both round-trip fine. `coerce_optional_cik` at both sites, plus `or existing_row.get("lenders_json")` at L1404.

- **L2147** `IMPORTANT` `[correctness]` **`name_class_sizes` misses legacy CIKs, silently disarming the `NAME_CLASS_GATE`** — Same root cause. A legacy row's unpadded CIK misses the padded key, so its name is not counted: the class size comes back 2 instead of 3, which flips the relaxed key rule from off to on. The comment on L2065 explains the stakes — FHLB Dallas files 67 identically named bonds with no dates and repeated round amounts, and without the gate one amount collision merges dozens of distinct bonds.

- **L717-748** `IMPORTANT` `[correctness]` **A planned retirement is forgotten when a newer amendment mention stops the scan, so the matcher asserts `repaid`** — `event_status_for_instrument` collects the pending flag while scanning but `break`s at the newest `entered_into`/`amended`, so an older mention's `expected_retirement` is never seen. With the amendment mention newer, `[p1]` gives pending `True` and `[p1, p2]` gives `False` — and downstream that is the difference between `active` and `repaid` on a row with a `retired_by` pointer. So adding an amendment mention makes the matcher claim a retirement the filings say is only planned, which is what the pending flag exists to prevent. The `break` is right for picking the deciding event; it just should not also gate `pending`. Computing `pending` in its own pass over all members would fix it.

- **L590-596, L679-680** `IMPORTANT` `[correctness]` **With two amendment children the parent is neither a head nor superseded, and reads `active`** — The pointer is nulled on ambiguity, but `is_lineage_head` reads the raw set and the status leg reads the nulled pointer. The parent ends up `head=False`, `superseded_by=None`, `status=active`: excluded from any head view, no forward pointer to follow, and reported alive even though the rollup knows two amendments replaced it. The single-child case is coherent, which is what makes this look like an oversight rather than a choice. Deriving the status from the set rather than the pointer fixes it.

- **L569-582** `IMPORTANT` `[correctness]` **`lineage_family_id` changes whenever the family grows** — The map is rebuilt each run and never seeded from existing rows, so the family key is whichever member's content hash happens to sort lowest — arbitrary rather than the oldest state, and changed by every new amendment. Anything that saves or links a family ID breaks on the next amendment. Seeding from an existing row's `lineage_family_id` in the component, falling back to `min`, would make it stable.

- **L526, L1813, L2002, L2011** `IMPORTANT` `[repo-coherence]` **The matcher respells extractor vocabulary it could import** — Four values are duplicated as literals, and the equalities were checked by evaluating them: `EXPECTED_RETIREMENT_KINDS` equals `TERMINAL_DATE_KINDS`, `TERMINAL_STATUS_EVENTS` equals the terminal kinds mapped through `STATUS_FOR_DATE_KIND`, `DERIVED_MATURITY_KINDS` equals the two `DERIVED_FROM_*` constants, and the bare `"-12-31"` is `YEAR_ONLY_MATURITY_SUFFIX`. This file already imports two names from `cdt.extractor.core` (L24-27), so the channel is open — and the extractor's own comment names the matcher as the consumer of the value the matcher then hardcodes. Adding a terminal kind upstream would silently fail to reach the matcher, with no test to catch it.

- **L584-587** `PREF` `[correctness]` **`matured` can flip backwards on a backfill** — `reference_date` is the newest filing date among *this run's* mentions, so backfilling an older filing can move an instrument from `matured` to `active`. It is also taken across a whole shard, so one issuer's recent filing decides whether a co-sharded issuer's older maturity reads `matured`. The docstring's determinism claim is true as written — it is reproducibility across *different* partitions that the incremental design needs. Would taking the max against existing `last_seen_filing_date` values work here?

- **L773-823** `PREF` `[correctness]` **`build_cluster_profiles` never sets `retired`, so the "prefer live over retired" tie-break is inert across runs** — `ClusterProfile.retired` is set only in `add_member`, which runs only for this run's mentions, so a pre-existing cluster whose row says `status="repaid"` still reports `retired=False`. The tie-break quietly degrades to "largest cluster" in exactly the incremental case it was written for. One line in the existing-instrument branch would restore it.

- **L1678-1687** `OPINION` `[correctness]` **A kind-only rate mention shadows an older complete one** — The predicate is `kind is not None or pct is not None`, so a newest mention with `kind="fixed"` and no verified pct beats an older mention carrying both, with no fallback slot — unlike `canonical_maturity_fields`, which keeps one for this exact shape. `kind="floating"` with a null pct is legitimately complete, so you can't just require the pct. Mirroring the maturity function would handle both.

- **L1090-1133** `OPINION` `[correctness]` **The `name_only_tie` branch emits no `related` edges** — It returns early, unlike the neighbouring branch, which publishes `related` for everything above the loose threshold. Nothing in the repo reads `related` today, so nothing observable is lost — just an asymmetry a future consumer would trip on.

- **L669-676** `OPINION` `[correctness]` **The recompute guard in `derive_instrument_status` is unreachable, and weaker if reached** — The rollup always passes `announced_instrument_ids`, and there is no other caller. If it ever were reached it would skip the announced-retirer check and return `repaid` for any `retired_by` pointer. The defaults also make "there genuinely is no event" impossible to express.

- **L944-955** `OPINION` `[correctness]` **Nothing recovers a same-item add-on merge** — Worth recording, not fixing. The removed test used *differing* start dates, so the old sibling guard never fired there and the add-on merged by name fingerprint; the new unconditional skip returns no candidate at all, and the add-on publishes as a second instrument. Lineage can describe the relationship but never recovers the merged `principal_amount`. I read this as the right trade — the merge it removes was actively wrong, publishing Gray Media's parent series at the add-on's $70M size — but the add-on case is now permanently split and that is not in the PR's known-gaps list.

- **L617, L625, L637** `PREF` `[repo-coherence]` **`_member_ids` rides in-band on output rows** — The same function already builds three side maps keyed by instrument ID for this purpose; a fourth would cost one line and remove the write/read/pop dance. No risk — I confirmed nothing leaks into the published dataset.

- **L94, L96** `PREF` `[repo-coherence]` **`maturity_source_mention_id` drops the `_date` its sibling keeps** — `start_date` → `start_date_source_mention_id`, but `maturity_date` → `maturity_source_mention_id`, two lines apart. The other five are group prefixes covering several columns each, which is deliberate and fine. Since the schema version is already bumping and the publisher doesn't read this schema yet, this is the cheap moment to align them.

- **L1525, L1538** `PREF` `[repo-coherence]` **`canonical_scalar_fields(existing_keys=...)` is never passed** — And the two functions it was built for inline the fallback by hand. They can't use it anyway, since they return multi-column dicts.

- **L1982** `PREF` `[repo-coherence]` **New code in the vocabulary this PR renamed** — `normalized_end_date_for_matching` touches only `maturity_*` columns. In fairness three neighbouring `end_date` names are inherited from `dev` unchanged, so it's locally consistent — but the PR grew the old-vocabulary island rather than shrinking it.

### src/cdt/extractor/core.py

- **L2814** `IMPORTANT` `[correctness]` **Two current `closing` dates pass a check the prompt advertises as validated** — The cap only counts kinds that are *not* event kinds, and `closing` is an event kind, so it is never counted: `closing` is accepted while `maturity`, `agreement` and `commitment_termination` are all correctly rejected. The prompt says "At most one current `agreement`, `closing`, `maturity`, or `commitment_termination` entry per object (validated)", and the retry message repeats it. Because nothing enforces it, `select_date_payload` publishes whichever date came first and drops the other with no retry and no failure record. The prompt's "(validated)" tags are the model's only signal that a rule is hard — eight of the nine are accurate, and this is the one that drifted.

- **L2899-2982** `IMPORTANT` `[correctness]` **The `amounts` list lost the multiple-values guard its predecessor still has** — `validate_dates_property` calls `validate_standardized_single_value_cardinality` per entry and the legacy `amount` property still routes through it, but the validator for the list that *replaced* `amount` never calls it. On one citation of `$2.5 billion` plus `$270.5 million`, `dates[0]` is rejected and `amounts[0]` is accepted. The accepted entry then publishes a null amount, because the parser picks the shorter span and the agreement check fails — so the figure is lost silently, which is exactly what the guard was written to prevent. One call mirroring the dates loop.

- **L3914-3924** `IMPORTANT` `[correctness]` **The documented name-derived principal fallback is dead code** — Two reviewers found this independently. The block calls `standardized_amount_payload(None, ...)`, whose result is gated behind an agreement check against the model's amount — which is `None` — so the synthesized payload's amount is always `None` and the block can never append anything. The docstring promises a synthesized principal entry "preserving #129". #129 is not regressed, since it still works whenever the model emits any `amounts` entry, but a `$183.36 million term loan` with no `amounts` entry publishes a null principal. The gate should probably also be `if not select_principal_amount(payloads)`, since a `prior` or unrelated `repayment` figure currently suppresses it too.

- **L4396-4399** `IMPORTANT` `[correctness]` **`lenders_known_incomplete` publishes `false` when an entry omits both `parties` and `dates`** — The new-schema shape is inferred from the presence of `parties` or `dates`, but the prompt tells the model to omit anything the document doesn't mention. An entry with only `name` and `amounts` matches neither test, falls through to the legacy path, and publishes "holders fully disclosed" beside an empty party list — affirmatively wrong, and the opposite of what the same entry reports if the model happens to include `dates: []`. Detecting the *legacy* shape by the presence of legacy keys would fix it.

- **L3596-3602, L3719-3725** `IMPORTANT` `[correctness]` **An unguarded `date()` call can abort the whole run, because a helper was copied without its guard** — `normalized_month_year_from_text` reimplements `iso_month_end_from_parts` 70 lines away (both new here) but drops its `is_valid_iso_date` check. So `"notes due January 0000"` raises `ValueError` where the guarded sibling returns `None`, and extreme tenors raise `ValueError`/`OverflowError`. Both are reached from `postprocess`, and the driver catches only `InfrastructureError` — so the exception unwinds past the registry save, the mentions write and the audit write, and the run dies having persisted nothing. The triggers are improbable; the blast radius is the entire job and the fix is to call the existing helper.

- **L3072-3077** `IMPORTANT` `[correctness]` **`validate_interest_rate` rejects the shape the prompt demonstrates** — An `interest_rate` with no `evidence` key is rejected; with `evidence: []` it passes. The prompt's own mini-example shows a rendered object with no `evidence` key, and the post-processor handles that shape perfectly — it verifies the rate off the instrument name and publishes it. So the strictness buys nothing and costs a full retry cycle on the one shape the prompt shows verbatim. Every other optional sub-object in the file tolerates an absent key. `value.get("evidence", [])`.

- **L4564, L4532** `IMPORTANT` `[correctness]` **The failure registry names a stage that succeeded and invents an error that didn't happen** — I found this replaying the run. A row salvaged at `instrument_ie` that then finishes normally ends `SUCCESS`, gets coerced to `PARTIAL`, and `_failure_record` never reads `salvage_notes`: it reports the last stage *run* and an error string built by `summarize_failure`, which finds no validation errors and returns `"Unexpected response at stage ..."`. The one PARTIAL row in the real run published `stage: instrument_relation` and that fabricated error, while its audit record shows that stage passed cleanly and the real loss — one entry dropped after three failed attempts — sat only in `salvage_notes`. `docs/schema.md` says the entry records what salvage dropped; here it names the wrong stage and describes a failure that did not occur, so an operator would re-run the wrong thing. All three callers are affected.

- **L4428** `IMPORTANT` `[correctness]` **`lenders_known_incomplete` now means two different things** — The derivation is internally consistent across extractor, matcher and docs, so the change was made properly; the question is what the flag now says. On the real window it is true for 517 of 669 mentions (77%, up from 56%), and **395 of those 517 are true only because no lender was named** — not because a collective phrase was present. The `dev` docs called that state "nothing to disclose rather than something undisclosed". Both states are still recoverable from `parties_json`, but the boolean a facet or badge binds to no longer separates them, and the matcher's `any(...)` plus the carry-forward makes it monotonic: once true, true forever. Keeping the boolean as "a collective cluster was present", or making it three-valued, would preserve the distinction.

- **L955-957** `IMPORTANT` `[migration]` **"Stored responses replay through postprocess" describes a path that doesn't exist** — There are two `postprocess` call sites, both inside `handle_response`, which always runs validation including the legacy-property rejection. Batch results go through the same function. So a stored `dev`-shaped response burns every attempt failing validation, then publishes as `PARTIAL` with a note saying it dropped nothing. The *semantics* do replay correctly — every "replay" claim in the docs holds — but the comment, the test name and four docs bullets all assert a bypass the code does not have. The realistic trigger is a rolling deploy with a batch in flight: retries append to the persisted conversation, so they still carry the old prompt and cannot produce new-shape output.

- **L2280** `OPINION` `[correctness]` **Salvage skips the legacy-property check, and `status_event` then overrides `dates`** — When the only failures were legacy-property rejections, nothing is dropped and the note reads "dropped 0 invalid ones". More consequentially, `postprocess` prefers a legacy `status_event` whenever it is present, so a mixed-shape salvaged entry resolves status from the old field and ignores its dated event facts. Publishing something rather than nothing is defensible for salvage; the precedence is the part that yields wrong data rather than merely old-shaped data.

- **L172-180** `PREF` `[correctness]` **`retirement` and `termination` ties break on response order** — Both have precedence 4, so a filing stating both on one date reports whichever the model listed first. The prompt explicitly anticipates the co-occurrence, so the pair is not hypothetical; both are terminal, so the harm is limited to the label.

- **L3100-3102** `PREF` `[correctness]` **`6-1/2%` reads as `2`** — The fraction pattern requires whitespace between the whole number and the numerator, so a common older-indenture spelling misses that branch and the percent pattern reads `2%` off the tail. Bounded by parser verification: the model's `6.5` fails to match and the rate publishes null, so it's a miss rather than a wrong value.

- **L198-202, L210, L947, L4020** `PREF` `[repo-coherence]` **Four new constant tables are unused, three shadowing hardcoded copies** — Verified at exactly one usage each. `DATE_COLUMN_KINDS` sits beside three hardcoded `select_date_payload(..., "closing"/"maturity"/...)` calls, `DATE_PRECISIONS` beside bare string returns, `FACILITY_INSTRUMENT_TYPES` is respelled inside `AMOUNT_KIND_TYPE_CONFLICTS`, and `LEGACY_STATUS_DATE_KINDS` has no use at all. ruff can't see unused module constants, so nothing else will catch them.

- **L4222-4227, L4487-4492** `PREF` `[repo-coherence]` **`expected_retirement_in_payloads` has no production caller while its predicate is inlined later** — One src usage (the definition), two test usages, and `relation_instrument_manifest` writes the same rule inline. Same rule, two places, and the copy with no caller can drift unnoticed.

- **L212-214** `PREF` `[repo-coherence]` **The `#141` comment ended up above the wrong constant** — It describes `STATUS_EVENT_VALUES` but now sits above `INTEREST_RATE_KINDS`, so the note about `matured` documents the interest-rate enum and the most important new enum in the schema has no comment.

- **L823-827, L971** `PREF` `[repo-coherence]` **Two new validators are positional where the five existing ones are keyword-only** — Six of the eight new ones follow the convention. The cost shows at the salvage call, where `0` is a meaningless placeholder that `index=0` would have made readable. This file's own pattern for a check family is a table plus a loop, which would settle the signature question and shorten the call sequence.

- **L218, L303, L3100** `PREF` `[repo-coherence]` **The rate marker is spelled three times instead of composed** — This file names regex fragments and interpolates them elsewhere, and this PR shows the hazard: it added `percent` to two of the three spellings. A named `RATE_MARKER` would fix it. (The broader claim that `rate_tokens` duplicates the existing rate machinery was checked and rejected.)

- **whole file** `PREF` `[repo-coherence]` **4,622 lines, with a verified clean seam** — Every other module here is under 1,400, and the repo's practice is to split a stage package once a concern separates. The seam was checked mechanically: ~1,870 lines contain no reference to the row state, the stage protocol, pandas, the storage helpers or settings, and `batch.py`'s twelve imports are all in the other half. `extractor/facts.py` plus `extractor/validators.py` would leave `core.py` around 2,700. Explicitly **not** for this PR — it would bury 2,982 reviewed lines under a file move. A follow-up issue is the right home.

- **L145, L155** `OPINION` `[repo-coherence]` **`TERMINAL_DATE_KINDS` lacks the grounding its neighbours carry** — It drives three separate behaviours and its membership is genuinely surprising: `default` is in the set, yet a default doesn't retire an obligation, and nothing says why an event of default counts as terminal here.

### src/cdt/extractor/prompts/instrument_ie.md

- **L99** `IMPORTANT` `[correctness]` **The validator restricts `prior` to commitment and principal; the prompt doesn't** — The prompt says only that `prior: true` marks a figure as it stood before a change, with no kind restriction. So a perfectly reasonable reading of "borrowings fell from $80 million to $60 million" — a current `outstanding_balance` plus a `prior` one — is rejected, burning the whole retry budget before salvage or a drop. The `dates` section *does* draw this line for its own flags, which makes the omission look accidental. One sentence would fix it.

- **L85-92** `IMPORTANT` `[correctness]` **The amount-kind/instrument-type rule is enforced but never stated** — The validator rejects `commitment` on a `note_bond` and `principal` on a revolver or credit line. The prompt's kind table implies the split but never forbids the pairing, and never says which of the two fields to change. The project's own error catalog lists this as an observed recurring model error, so these retries will actually be spent — and an item whose only amount carries the wrong kind loses the amount entirely after salvage.

- **L106** `IMPORTANT` `[correctness]` **A worked mini-example fails validation when followed** — The example maps "will repay $68 million in outstanding amounts under the credit facility" to a `repayment` amount with no instruction to add a matching `repayment` date entry. An object that follows it and also records the facility's `agreement` date — which the prompt separately asks for — is rejected. The rule only escapes when `dates` is empty, which for a named facility is rare. The error catalog notes that examples steer this model harder than rules do, so this is the highest-leverage line of the set.

- **L110** `PREF` `[correctness]` **Nothing enforces "no `rate_pct` for a floating rate"** — The prompt is unambiguous that benchmarks and margins aren't recorded, but the validator checks `kind` and `rate_pct` separately and never against each other. A `floating` rate with `rate_pct: "0.875"` citing a `0.875% per annum` span passes and publishes — and that is issue #29's exact value, in the column #157 added to fix it. I'm calling this preference rather than important because I measured it: **0 of 70 floating mentions** in the real run published a rate. The model obeyed the prompt every time, so #29 isn't regressed — but the fix currently rests entirely on model obedience, and three lines would close it.

- **L62** `OPINION` `[correctness]` **`expected` is also set from the calendar** — Any non-announcement event dated after its filing is marked expected regardless of what the model said. Well motivated and well commented, but it means model output and stored fact differ silently. One clause would state the invariant the code already enforces.

### src/cdt/extractor/core.py (canonical name selection)

- **L3297-3305** `IMPORTANT` `[correctness]` **The canonical name picks the agreement name over the facility name, against `ner.md` rule 11** — `name_text` is the single longest `name` span, while the NER prompt now says the descriptive phrase "must never be dropped in favour of the agreement name" and the IE prompt says to include every span. Multi-span names are the norm — **476 of 669 mentions (71%)** — and I measured **9 real cases** where the longest-span rule does what rule 11 forbids: `'Amended and Restated Credit Agreement'` beating `'revolving credit facility'`, `'Second Amended and Restated Credit Agreement'` beating `'term loan B facility'`, `'Super-Priority Senior Secured Priming DIP...'` beating `'DIP Facility'`. It matters past display, because the published name feeds `normalize_name_fingerprint` — so the picker manufactures exactly the generic template names that the matcher's own generic-name guard and `NAME_CLASS_GATE` exist to work around. Preferring a span that isn't agreement-shaped, or one carrying a concrete term, would fix it. (The related claim that this also kills the `due 2028` maturity backstop is mechanically true but measured **0** real occurrences, so it's a note rather than a finding.)

### docs/schema.md

- **L207, L259, L264** `IMPORTANT` `[correctness]` **Four inaccuracies in the file the publisher will be written against** — (1) L207 says a projected close appears in `dates_json` as `expected_closing`; the post-processor rewrites that kind before publishing, and across the real run **0 of 1,173 date facts carry it** while 40 `closing` facts carry `expected: true` — and the file's own `dates_json` bullet correctly omits it, so the document contradicts itself. Also unstated: an `agreement`-only mention publishes `entered_into`, and `commitment_termination_date` "Null for notes and bonds" is unenforced — worth noting since the analogous amount-kind rule *is* enforced, so a reader reasonably infers this one is too.

- **L11, L200, L249** `PREF` `[correctness]` **The CIK padding contract isn't true of any partition** — Padding happens in exactly two places, the ingest manifest reader and the snapshot writer; no stage in between pads. In `data/schema-smoke` and `data/genwindow-batch-smoke` the mention CIKs are unpadded (`816761`) while the instrument CIKs are padded, in one artifact root. The global bullet is honest about the snapshot mechanism, but the per-dataset bullets claiming the *partition* column is padded are not. Either add one `normalize_cik` call where mentions are built, or reword the three bullets.

### src/cdt/datasets.py
